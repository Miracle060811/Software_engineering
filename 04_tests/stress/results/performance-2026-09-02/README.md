# 单体与微服务性能对比记录（2026-09-02）

## 1. 结论

在同一台机器、相同查询条件、相同 k6 脚本和相同 5→10→20→50 VU 阶梯负载下，`monolith-start` 与当前六微服务版本分别完成 2 个场景、每场景 3 次正式运行，共 12 次。所有运行的 k6 退出码均为 `0`，HTTP 错误率均为 `0`。

本轮观测中，微服务查询接口的平均响应时间和 P95 均低于单体基线；但脚本包含每次迭代 `sleep(0.5)`，吞吐量主要受固定思考时间约束，不能据此宣称系统达到最大吞吐能力，也不能把本机结果外推为生产环境结论。

## 2. 环境与可比条件

- 操作系统：Microsoft Windows 11 家庭版中文版
- CPU：13th Gen Intel(R) Core(TM) i5-1340P，16 logical processors
- 内存：15.7 GiB
- Docker Desktop：4.66.1；Docker Engine：29.3.1
- JDK：Eclipse Temurin 21.0.11
- k6：2.2.0
- 单体基线：Git tag `monolith-start`，commit `7258cd2ccfcdf0b66c79010f0653da2bae81a29a`
- 微服务基线：commit `dde8b3299b8b83f0ebad5fcb2a410b96b36155b2`
- 查询数据量核对：北京→上海航班在两个版本中均返回 4 条；北京酒店在两个版本中均返回 5 条。
- 单体使用隔离 MySQL/Redis 与宿主 Java 进程；微服务使用独立 Compose project、六套 MySQL 和 Redis。

## 5. CPU 与内存边界

资源原始采样已经随每轮结果保存：单体通过 Windows Java 进程每 2 秒采样；微服务通过 `docker stats` 对目标服务容器采样。由于两个版本的 CPU% 采集口径不同，资源数据用于描述各自运行状态，不做直接百分比优劣结论。

## 6. 原始证据

`monolith/` 与 `microservices/` 各保存 30 个文件，包括：

- `*-k6-summary.json`：k6 原始统计；
- `*-k6.stdout.log` / `*.stderr.log`：完整运行输出；
- `*-resource-samples.csv`：逐次 CPU/内存样本；
- `*-resource-summary.json`：每轮资源汇总。
