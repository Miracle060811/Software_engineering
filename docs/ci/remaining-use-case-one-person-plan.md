# TravelMate 剩余 11 个用例单人补全计划

## 1. 目标与完成标准

由一名执行者连续完成 UC01、UC02、UC03、UC05、UC06、UC07、UC08、UC11、UC12、UC18、UC19 的自动化验收闭环。

每个用例只有同时满足以下条件，才允许从 `partial` 改为 `covered`：

1. 至少有一组后端 UNIT/INT 测试，验证主流程、关键异常流和数据副作用。
2. `frontend/tests/e2e-real/travelmate-real.spec.js` 中存在真实 MySQL/Redis 服务 E2E 流程。
3. 失败路径包含明确断言，不能只检查 HTTP 请求未报错。
4. `docs/ci/use-case-test-matrix.json`、业务场景清单和追溯文档状态一致。
5. 本地全量测试、追溯门禁和 PR CI 全部通过。

最终量化目标：19 个 `covered`、0 个 `partial`、0 个 `planned`，自动化证据分 38/38。

## 2. 单人执行顺序

### 阶段 A：建立剩余基线与测试数据边界

- 核对 11 个用例的 Controller、Service、Mapper、数据库表和现有 E2E 接口。
- 复用现有随机用户、管理员、旅客和资源数据，避免测试相互污染。
- 为新增测试统一命名：`UseCaseXX...Tests`、`E2E-TC-1XX`。
- 保留工作区中与测试无关的未提交文件，不混入测试提交。

验收：计划文件、缺口映射和拟新增测试文件一一对应。

### 阶段 B：交易与库存链路（UC02、UC03、UC05、UC06、UC07）

#### UC02 航班查询与预订

- 后端：本人旅客成功下单、库存原子扣减失败、旅客越权、非法票数、优惠券失败不建单。
- E2E：查询航班 → 选择旅客 → 创建订单 → 验证订单金额与库存变化。

#### UC03 火车票与候补

- 后端：一/二等座成功下单、库存不足、旅客越权、候补创建与重复候补。
- E2E：车次查询 → 购票或候补 → 验证订单/候补结果。

#### UC05 酒店搜索与订房

- 后端：有效日期成功订房、日期边界、库存不足、房间数校验、失败不产生脏订单。
- E2E：搜索酒店 → 读取房型 → 创建待支付订单 → 验证订单详情。

#### UC06 酒店订单状态与库存回补

- 后端：支付、取消、退款、重复操作、越权、超时关闭及精确回补库存。
- E2E：创建酒店订单 → 支付/取消/退款 → 验证状态和凭证权限。

#### UC07 景点购票

- 后端：成人/儿童票金额、非法数量、资源下架、越权凭证、失败不建单。
- E2E：查询景点 → 购票 → 查询本人订单和凭证。

验收：5 个用例各有后端测试与真实 E2E，数据库状态和库存副作用可断言。

### 阶段 C：账户与公共浏览（UC01、UC08）

#### UC01 注册、登录与账户安全

- 后端：重复用户名、错误密码、禁用账号、改密、注销、普通用户访问管理员接口。
- E2E：注册 → 登录 → 访问本人信息 → 旧密码失效/新密码可用。

#### UC08 一日游/周边游浏览

- 后端：分类列表契约、行程步骤、空列表、非法参数。
- E2E：匿名切换分类 → 展示产品字段与步骤 → 空状态/错误状态。

验收：安全副作用和公开浏览契约均有可重复证据。

### 阶段 D：AI 行程与多轮客服（UC11、UC12）

#### UC11 AI 行程

- 后端：正常结构化响应并落库；无 Key、超时、HTTP 错误、非法 JSON 三类降级；错误结果不落脏数据。
- E2E：生成行程 → 查询历史 → 打开详情，验证用户隔离和结构化字段。

#### UC12 AI 多轮客服

- 后端：同一 `session_id` 保留上下文；新会话隔离；空/超长消息、会话越权和外部失败。
- E2E：连续两轮提问 → 验证会话标识、顺序和历史恢复。

验收：外部 AI 使用可控 stub，不依赖真实密钥或不稳定网络。

### 阶段 E：后台管理与内容安全（UC18、UC19）

#### UC18 管理后台

- 后端：管理员资源维护、用户启停、订单审核、非法库存、目标不存在、普通用户 403。
- E2E：管理员登录 → 修改资源/用户/订单 → 验证结果；普通用户访问失败。

#### UC19 内容安全与可观测性

- 后端：帖子审核、举报处理、敏感词增删、重复终态、日志/统计失败降级。
- E2E：管理员完成举报与敏感词闭环，并查询日志/仪表盘。

验收：RBAC、终态幂等和审计副作用都有断言。

### 阶段 F：追溯、回归与 CI 收口

- 将 11 个用例逐项改为 `covered`，不得批量先改状态后补证据。
- 将质量门禁从 27 提升到 38，保持 `coveredRequiresBothLayers=true`。
- 同步 `document/业务场景清单与用例说明.md`、`document/需求设计代码测试追溯表.md` 和测试执行报告。
- 更新测试运行手册与最终统计。
- 执行完整本地回归并推送 PR，等待 CI、真实 E2E、CodeQL 和安全扫描全部通过。

最终验收命令：

```powershell
mvn -f backend/pom.xml test
npm --prefix frontend run test:unit
npm --prefix frontend run lint
npm --prefix frontend run build
npm run test:e2e
npm run check:traceability
git diff --check
```

## 3. 提交策略

- 每个阶段单独提交，提交中只包含该阶段测试、必要修复和对应追溯更新。
- 测试发现业务缺陷时，先用失败测试固定现象，再做最小修复。
- 不提交 `backend/target`、`frontend/dist`、Playwright 临时报告等生成物。
- 不合并 PR，除非用户明确授权。

## 4. 风险与停止条件

- 若真实 E2E 需要当前数据库不存在的稳定资源，新增专用、可重复初始化的测试数据。
- 若外部 AI/实时交通接口不可用，使用契约级 stub 验证降级，不把网络波动算成功。
- 任一测试失败时停止后续发布步骤，记录失败原因并修复后重跑。
- 不以覆盖率数字替代业务场景验收；覆盖率只作为补充证据。
