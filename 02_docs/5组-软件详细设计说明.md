## 1 引言

### 1.1 编写目的

本文档旨在对“TravelMate（伴游）”智能旅游平台进行详细设计说明。在概要设计的基础上，进一步明确系统各模块的实现算法、数据结构、接口细节及业务逻辑。

本文档的预期读者包括：前端开发工程师、后端开发工程师、测试工程师、运维工程师以及项目管理人员。通过本说明书，可指导系统编码实现、模块联调以及后续测试与维护工作。

本文档以《5 组—软件需求规格说明》和《软件概要设计说明书》为设计基线，采用稳定编号建立需求、用例、设计、代码和测试之间的追溯关系。

### 1.2 背景

- **软件名称**：伴游（TravelMate）出行旅游平台
- **任务提出者**：软件工程基础 2026 春课程组
- **开发者**：Miracle 开发小组
- **开发团队**：四人小组，成员 A—D 分别负责大交通、目的地与本地生活、AI 服务、社区与用户中心；管理后台与可观测性子系统由成员 D 兼任负责。
- **预期用户**：旅游游客、旅游内容创作者、平台运营与管理人员。
- **运行与部署环境**：
  - **开发与测试环境**：团队成员个人计算机，支持 Chrome、Edge 等主流 Web 浏览器。
- **核心技术栈选型**：
  - **前端**：Vue 3 + Vite + Element Plus + Pinia + Axios。
  - **后端**：Java 21 + Spring Boot 3.5.13 + MyBatis-Plus 3.5.7。
  - **认证**：Spring Security + jjwt 0.11.5（HS256 对称密钥，24h 过期）。
  - **数据存储与中间件**：MySQL 8.0、Redis 缓存中间件。
  - **AI 能力接入**：封装 DeepSeek API（OpenAI 兼容协议，默认模型 `deepseek-v4-flash`），行程规划要求结构化 JSON 输出；API 不可用时自动降级为本地模板。

## 2 系统结构设计及子系统划分

本项目采用前后端分离的系统架构。后端基于 Java 21 + Spring Boot 3.5.13 + MyBatis-Plus 3.5.7 构建 RESTful 风格的服务端接口，前端采用 Vue 3 + Vite + Element Plus 实现响应式交互界面。在数据交互上，各模块优先统一核心数据模型（用户、订单、资源、消息等），确保不同成员开发的模块能够顺利进行集成联调。

![系统总体架构图](./详细设计说明/01_系统总体架构图.png)

按照项目团队的开发分工与核心业务流，我们将系统整体划分为以下五个核心子系统：

**1. 大交通票务与订单子系统（设计责任：成员 A）**

- **功能职责**：负责平台核心大交通资源的预订与基础订单生命周期管理。
- **核心设计**：不接入真实商业票务系统，机票与火车票数据优先采用本地 Mock 数据与数据库初始化数据支撑。实现车次/航班实时查询、多平台模拟比价、历史价格走势展示。统一管理平台基础订单模型，包含订单状态机流转控制、模拟支付接口对接、库存预占调用以及退款处理逻辑。

**2. 目的地住宿与本地生活子系统（设计责任：成员 B）**

- **功能职责**：以最小可交付范围负责酒店、景点基础浏览，以及行后评价提交与展示。
- **核心设计**：实现酒店多维度搜索过滤、酒店 / 景点详情展示、基础五星图文评价提交与列表展示。酒店订单支持按 `roomCount` 多房间预订，景点门票订单写入 `tm_attraction_order` 并提供订单/凭证展示；商家回复、评价举报处理、酒店 / 景点后台维护由 E 的管理后台负责。

**3. AI 智能规划与 Agent 服务子系统（设计责任：成员 C）**

- **功能职责**：负责平台所有与大语言模型相关的智能化场景以及全局消息触达。
- **核心设计**：统一封装 DeepSeek API。行程规划模块要求模型返回严格 JSON，失败时回退到本地模板，保障前端稳定渲染；AI 客服结合站内业务数据提供旅行问答，但不编造实时库存、价格或订单状态。此外，负责统筹平台通知服务（站内信、红点未读逻辑），并在订单、审核、退款和 AI 规划场景中触达用户。

**4. 旅途社区与用户中心子系统（设计责任：成员 D）**

- **功能职责**：承担全平台的用户认证鉴权、社交互动与内容沉淀。
- **核心设计**：实现基于 **JWT** 的安全登录注册与用户信息管理；提供 UGC 内容发布工具（多图上传、地理位置打卡）；搭建兼容图文与视频的**双列瀑布流**交互界面；构建包含关注/粉丝体系、点赞收藏与树状评论结构的社交关系链。

**5. 管理后台与可观测性子系统（设计责任：成员 D）**

- **功能职责**：面向平台管理员，提供资源维护、安全审核与系统运行状态监控。
- **核心设计**：搭建基于 **RBAC（基于角色的访问控制）** 的权限与安全架构；实现轻量数据可观测仪表盘（如订单统计、日志看板、用户与内容统计）；构建内容与安全审核防线（社区图文敏感词自动过滤 + AI 辅助审核 + 人工审核工作流）；提供大交通、酒店、房型、景点、目的地基础数据的后台 CRUD、CSV 导入、退款审核、商家回复和评价举报工单处理等运营侧功能。

**子系统间的协同关系说明：**

- 子系统 A 与 B 重点围绕**交易履约流程和库存控制模型**进行底层协同；
- 子系统 C 在生成行程与智能问答时，需跨模块调用 A/B 提供的资源检索接口（Mock 数据共享）；
- 社区模块生成的 UGC 内容进入管理后台审核流完成安全合规校验；社区与管理后台统一使用内容状态和审核接口完成联调。

### 2.5 正式用例说明

| 用例 | 触发条件与前置条件 | 主成功流程 | 备选/异常流程 | 可验证结果 |
| :--- | :--- | :--- | :--- | :--- |
| UC01 用户注册、登录与账户安全 | 游客提交注册或登录；注册用户名未占用 | 校验输入 → BCrypt 保存/比对密码 → 生成 JWT → 前端保存 Token → 后续请求携带 Bearer Token | 用户名重复、密码错误、Token 过期或账号禁用时返回业务错误并拒绝访问 | `tm_user` 正确新增或登录返回 Token；匿名访问受保护接口得到 403 |
| UC02 查询并预订航班 | 用户选择出发地、目的地、日期；下单前已登录并已选择乘客 | 查询航班 → 选择舱位和乘客 → 校验库存/优惠 → 原子扣减 → 创建待支付交通订单 | 无结果、库存不足、参数非法或重复提交时不创建订单 | `tm_traffic_order` 新增，`tm_flight.available_seats` 按票数扣减 |
| UC03 查询并预订火车票或提交候补 | 用户输入车站与日期；下单前已登录 | 查询车次 → 选择席别/乘客 → 有票则扣减并建单，无票可提交候补 | 公共余票同步失败时回退本地数据；库存不足进入候补或提示失败 | 订单或 `tm_train_waitlist` 记录可查，库存不为负数 |
| UC04 交通订单支付、取消、退款与凭证查看 | 用户对本人交通订单执行支付、取消、退款或查看凭证 | 校验订单归属和当前状态 → 执行合法状态迁移 → 记录支付/退款 → 必要时回补库存 → 返回凭证 | 非法状态跃迁、重复操作、越权访问被拒绝；退款需管理员审核时进入待审核 | 状态机符合“待支付→已支付/已取消→已出行/退款”；库存与订单一致 |
| UC05 搜索酒店并完成订房 | 用户输入城市和入住日期；下单前已登录 | 搜索酒店 → 查看详情/房型 → 输入入住人与房间数 → Redis 预减 → 数据库原子扣减 → 创建待支付酒店订单 | Redis 不可用时降级数据库校验；库存不足、日期非法或参数缺失时失败 | `tm_hotel_order` 新增，房型库存按 `roomCount` 扣减且不超卖 |
| UC06 酒店订单支付、取消、退款与库存回补 | 用户操作本人酒店订单 | 支付确认 → 状态更新；取消/退款 → 校验状态 → 回补 Redis 与数据库库存 → 返回结果 | 超时未支付由调度器关闭并回补；重复退款、越权或非法状态拒绝 | 状态和库存最终一致，重复请求不造成重复回补 |
| UC07 景点浏览与购票 | 用户浏览景点并提交购票信息 | 查询景点 → 查看详情 → 选择成人/儿童票 → 校验票量 → 创建景点订单 → 查看凭证 | 票量不足、游客信息无效或未登录时不创建订单 | `tm_attraction_order` 新增，票数与金额计算正确 |
| UC08 选择并预订一日游或周边游产品 | 游客浏览产品；提交预订前用户已登录并选择日期、人数和联系人 | 查询产品与行程 → 选择班期、人数和联系人 → 校验价格与库存 → 扣减库存 → 创建订单并返回结果 | 产品下架、班期不可售、库存不足、未登录、联系人无效或重复提交时失败且不产生脏订单 | 成功时本地游订单可查；失败时不扣库存、不产生脏订单 |

## 3 功能模块设计

### 3.1 AI 行程生成模块

- **模块描述**：根据用户输入生成个性化旅游行程，并与平台 Mock 资源进行关联匹配。
- **模块编号**：TM-MOD-01
- **输入**：目的地（String）、天数（Int）、预算范围（Float）、出行人数（Int）、偏好标签（List）
- **处理**：
  1.  对用户输入进行合法性校验。
  2.  构造标准化 Prompt（模板化 + 变量参数填充）。
  3.  异步调用 DeepSeek API 获取行程推荐结果。
  4.  使用 JSON Output 约束，对返回结果进行严格的结构化校验。
  5.  对不完整字段进行本地模板补全；DeepSeek 未配置、超时或 JSON 解析失败时，自动降级为可展示的本地行程 JSON。
  6.  结合本地酒店、景点及交通数据生成推荐说明，并将生成结果持久化到 `tm_ai_plan`。
  7.  **规范化记录：对 Prompt、AI 对话、行程结果和通知触达进行落库或日志留存，便于复盘。**
- **算法与调用描述**：
  采用 Prompt Engineering + 结构化 JSON 约束，结合本地 Mock 景点数据与热门行程模板。DeepSeek Chat Completions 调用由 `AiServiceImpl` 封装，模型输出解析失败时走本地降级模板，以保证前端 `AiPlan.vue` 稳定渲染。
  **大模型相关用途、Prompt 模板、配置项和降级策略见同目录下的 [`大模型使用说明.md`](./大模型使用说明.md)，确保模型使用的可解释性与可追溯性。**
- **输出**：行程 JSON 数据（按天划分）、推荐资源列表、行程摘要信息。

### 3.2 订单库存管控模块

- **模块描述**：面向小并发运行环境，负责机票、酒店等资源在预订过程中的防超卖控制与数据一致性保证。
- **模块编号**：TM-MOD-02
- **输入**：商品 ID（Mock 资源主键）、预订数量、用户 ID
- **处理**：
  1.  **Redis 缓存预减**：酒店房型下单时优先在 Redis 中按 `roomCount` 执行 Lua 预减，快速拦截非法/超量请求；Redis 不可用时降级为数据库扣减。
  2.  **数据库原子校验**：订单落库时，放弃重量级的行级悲观锁，**采用数据库原子更新语句**进行库存校验（例如：`UPDATE tm_hotel_room SET available_rooms = available_rooms - #{count} WHERE id = ? AND available_rooms >= #{count}`）。航班、火车、酒店、景点均按实际 `ticketCount` / `roomCount` 扣减。
  3.  生成待支付订单，标记库存处于“预占”状态。
  4.  接收到支付成功回调后，正式确认为已售库存。
  5.  超时未支付的订单（15 分钟），通过 `OrderTimeoutScheduler` 定时任务触发库存回滚，恢复 Redis 与数据库中的剩余可用量。
- **算法策略描述**：
  不使用企业级庞大复杂的分布式锁方案，采用“Redis 缓存预减 + 数据库原子更新语句 + 超时回滚”的组合策略。该策略既能有效防止资源超卖现象，又能充分验证小并发场景下系统处理关键业务的并发安全性。
- **输出**：锁定成功 / 失败状态标识、最新库存余额。

### 3.4 基础订单管理模块

- **模块描述**：统管大交通与酒店业务线的生命周期，构建业务闭环的基石。
- **模块编号**：TM-MOD-04
- **输入**：各业务线生成的预留单、外部支付指令（模拟）、用户侧操作指令（取消/确认出行/评价）。
- **处理**：
  1.  统一订单模型落库：生成全局唯一的订单流水号，聚合资源信息与用户信息。
  2.  模拟支付接口（Mock）处理：不接入微信/支付宝等真实商业支付系统，而是由系统内部提供统一的“支付确认”Mock 接口（或本地桩代码），模拟支付成功并主动触发 Webhook 回调服务。
  3.  核心订单状态机流转控制：管理订单的阶段演进，校验状态跃迁的合法性。定义基础流转路径：【待支付】 -> 【已支付 / 已取消】 -> 【已出行（履约）】 -> 【已评价 / 退款处理】。

- **算法与业务逻辑描述**：
  基于状态机（State Machine）模式实现订单流转。每次状态变更须校验 `expected_current_state`（预期当前状态），防止因小并发点击导致的状态乱序。通过对支付环节进行 Mock 模拟，将重点集中于验证从“行前规划、下单预占”到“行中履约”、“行后评价”的完整业务闭环真实性。

### 3.5 用户认证与安全模块

- **模块描述**：负责全平台统一身份认证、会话管理与角色权限控制，是所有业务模块的安全基础。
- **模块编号**：TM-MOD-05
- **输入**：注册请求（用户名 / 邮箱 / 手机号 / 密码）、登录请求（用户名 + 密码）、HTTP 请求 Header 中的 Bearer Token。
- **处理**：
  1.  **注册流程**：接收注册信息，进行格式校验（长度、邮箱格式等），检查用户名唯一性，使用 BCrypt 对密码进行加盐哈希加密后落库（`tm_user` 表）。
  2.  **登录流程**：查询用户，用 `BCryptPasswordEncoder.matches()` 校验密码，校验通过后使用 jjwt 0.11.5（HS256 对称密钥）生成 JWT，过期时间 24h，连同用户基础信息一并返回给前端。
  3.  **JWT 拦截验证**：`JwtFilter` 在 Spring Security 过滤链中拦截每个请求，从 `Authorization: Bearer <token>` Header 提取 token，解析有效性与过期时间，将 username 设入 `SecurityContextHolder`。
  4.  **权限控制（RBAC）**：`SecurityConfig` 按接口路径配置白名单（`/user/register`、`/user/login`、`/user/reset-password`、航班/火车/酒店/景点/目的地/游记列表等只读 GET 接口），其余接口均需认证。管理员接口 `/api/admin/**` 通过 `ROLE_ADMIN` 校验。
  5.  **UserContext 工具**：Controller/Service 层通过 `UserContext.getCurrentUserId()` 获取当前登录用户 ID，内部从 `SecurityContextHolder` 取 username 再查库。
- **关键设计决策**：
  - JWT 使用每次重启重新生成的内存对称密钥，旧 token 重启后全部失效（课程项目场景可接受，保证实现简单）；
  - 密码不可逆 BCrypt 存储，满足 OWASP 密码安全要求；
  - `User` 实体 `@TableName` 值为 `"tm_user"`，非 MyBatis-Plus 默认推导的 `"user"`。
- **输出**：JWT Token（登录成功）、用户详情 DTO、403/401 JSON 错误响应。

  1.  **酒店搜索**：多条件组合查询（城市、日期、价格区间、星级、设施标签），返回酒店列表及首图摘要。
  2.  **房型展示与库存展示**：查询指定酒店的所有房型，实时展示剩余可用库存（从 Redis 缓存或数据库查询）。
  3.  **房务预订 & 防超卖**：酒店订单接口已落地，支持按 `roomCount` 预订多间房；Redis 预减、数据库原子扣减、订单状态流转由 TM-MOD-02 统一约束。
  4.  **景点 / 本地玩乐**：提供景点列表与详情展示；门票购买入口通过 `/api/attraction/{id}/ticket` 提供，订单写入 `tm_attraction_order`，订单/凭证展示用于演示核销流程。
  5.  **评价体系**：成员 B 负责用户 1-5 星评分 + 图文评价提交与列表展示；商家回复（`tm_reply`）、评价举报（`tm_review_report`）及举报工单处理由成员 D 负责的管理模块统一维护。
- **关键实体**：`tm_hotel`、`tm_hotel_room`、`tm_hotel_order`、`tm_attraction`、`tm_attraction_order`、`tm_tour_product`、`tm_tour_product_step`、`tm_media_asset`、`tm_review`、`tm_reply`、`tm_review_report`。
- **输出**：酒店 / 景点列表 JSON、酒店 / 景点详情 JSON、基础评价提交与列表结果。

### 3.7 旅途社区与用户中心模块

- **模块描述**：承担全平台 UGC 内容发布、社交关系与互动，以及用户个人中心管理。
- **模块编号**：TM-MOD-07
- **输入**：图文帖子（标题 + 正文 + 图片 URL + 话题标签）、点赞 / 收藏 / 评论请求、关注 / 取关请求。
- **处理**：
  1.  **内容发布**：接收帖子创建请求，进行敏感词过滤（`SensitiveWordService`），过滤通过后写入 `tm_post`，状态置为"审核中"（0）或"已发布"（1）；图片文件上传至本地存储，URL 写入帖子字段。
  2.  **内容流**：首页推荐流按热度（点赞 + 评论加权）+ 时间衰减排序；关注流按 `follow` 关系过滤用户发布的帖子，分页返回。

  4.  **关注关系**：`tm_follow` 记录 `follower_id` → `followee_id`，关注成功后推送站内通知。
  5.  **用户中心**：支持头像上传（文件接口）、个人资料修改、查看我的发布 / 点赞 / 收藏列表，以及修改密码。
- **关键实体**：`tm_post`、`tm_comment`、`tm_like`、`tm_follow`、`tm_user`、`tm_notification`。
- **输出**：帖子列表 / 详情 JSON、互动操作结果、用户主页数据 DTO。

### 3.8 管理后台与可观测性模块

- **模块描述**：面向管理员的运营管理、内容审核、系统监控与权限控制。

- **模块编号**：TM-MOD-08

- **输入**：管理员操作指令（资源 CRUD、内容审核、用户管理）、定时采集任务触发信号。

- **处理**：
  1.  **资源管理**：航班、火车、酒店、房型、景点、目的地的后台增删改查，支持 CSV 批量导入与库存调整。
  2.  **内容审核**：对 `status=0`（待审核）的帖子进行人工审核，通过则置 `status=1`，拒绝则置 `status=2` 并记录原因；支持一键封禁用户。
  3.  **优惠券管理**：创建满减 / 折扣优惠券（`tm_coupon`），设置发行量、使用规则、有效期和业务分类（通用/机票/火车票/酒店）；查看用户领券记录（`tm_user_coupon`）。
  4.  **系统日志与 AOP 审计**：`SysLogAspect` 通过 AOP 自动拦截所有 `com.travelmate.controller` 下的方法，记录方法名、参数摘要、耗时、操作用户、IP 及成功 / 失败状态到 `sys_log` 表，日志落库失败不影响业务。
  5.  **接口限流（RateLimiter）**：`@RateLimiter(maxRequests, timeWindowSeconds)` 注解作用于高频写接口（下单、支付），`RateLimiterInterceptor` 基于 Redis 计数器 + IP 拦截超限请求，返回 HTTP 429。
  6.  **可观测大屏**：统计用户数、订单总量、收入、帖子、举报、优惠券等指标；数据来源为业务表和 `sys_log` 聚合，前端使用 ECharts 可视化展示。
  7.  **举报工单**：查看 `tm_review_report` 举报列表，支持驳回或删除被举报评价。
  8.  **敏感词维护**：动态添加 / 删除敏感词库，立即生效于发帖审核流程。

- **关键实体**：`sys_log`、`tm_coupon`、`tm_user_coupon`、`sys_sensitive_word`、`tm_review_report`、`tm_reply`、`tm_destination`。

- **输出**：管理操作结果、审核结果、可观测统计 JSON（供前端 ECharts 渲染）。

### 3.9 用例域的组件级与对象级设计

本节从组件静态协作和对象动态交互两个角度补充模块设计。组件图用于说明前端、Controller、Service、Mapper、数据库及外部依赖之间的职责边界；对象级顺序图则以一次完整业务请求为线索，展示关键方法调用、状态变化及异常处理分支。

#### 3.9.1 大交通与订单域（UC02—UC04、UC16）

大交通域由航班、火车、交通订单和常用旅客四类组件组成。查询请求分别进入 `FlightController` 与 `TrainController`，订单创建、支付、取消和退款统一由 `TrafficOrderController` 协调；Service 层负责库存校验和状态机控制，Mapper 层持久化资源、候补、订单与旅客数据。公共余票同步和 Redis 仅作为辅助能力，失败时不能破坏本地订单主流程。

![大交通与订单域组件图](./详细设计说明/14_大交通与订单域组件图.png)

对象级顺序图以用户创建交通订单为起点：系统先校验资源与库存，再写入待支付订单并进行库存预占。支付成功后更新订单状态并发送通知；用户取消时释放库存；库存不足或越权访问则在写入订单前终止流程，从而保证订单归属和库存数据一致。

![大交通订单代表流程对象级顺序图](./详细设计说明/15_UC02_大交通订单代表流程对象级顺序图.png)

#### 3.9.2 酒店、景点与权益域（UC05—UC10）

酒店景点域覆盖酒店与房型、景点门票、评价回复、评价举报、优惠券及本地游产品。各 Controller 只处理参数和响应，具体业务由对应 Service 完成；酒店库存采用 Redis Lua 预减与数据库原子扣减组合，评价和举报通过独立数据表形成提交、回复、举报、处理的闭环。

![酒店景点与权益域组件图](./详细设计说明/16_酒店景点与权益域组件图.png)

酒店预订顺序图展示了正常预订、库存不足、Redis 降级、支付、主动取消和超时回滚等分支。数据库是库存最终事实源：Redis 不可用时直接执行数据库原子扣减；订单取消或超时关闭时，同时回补缓存与数据库库存，并通过订单状态防止重复回补。

![酒店预订与退款对象级顺序图](./详细设计说明/17_酒店预订与退款对象级顺序图.png)

#### 3.9.3 AI 与消息域（UC11—UC13）

AI 与消息域由行程页面、AI Controller、AI Service、模型接口、本地降级模板、计划/对话 Mapper、通知中心和私信服务组成。DeepSeek API 被视为可失败的外部依赖，模型响应必须经过结构化校验后才能持久化和展示，通知或私信发送失败不得导致已生成的行程回滚。

![AI与消息域组件图](./详细设计说明/18_AI与消息域组件图.png)

行程生成顺序图从参数校验开始，依次执行 Prompt 构造、模型调用、JSON 解析、本地资源匹配、结果落库和通知发送。当 API Key 缺失、请求超时或返回内容不符合结构约束时，系统切换到本地模板并显式标记降级结果，保证前端始终获得可渲染的数据结构。

![AI行程生成对象级顺序图](./详细设计说明/19_AI行程生成对象级顺序图.png)

#### 3.9.4 社区与用户关系域（UC14、UC15、UC17）

社区域围绕帖子、评论、点赞收藏、关注关系、用户主页和文件上传展开。帖子发布前由敏感词服务执行内容检查，审核调度器和管理员共同控制帖子状态；点赞、评论、关注等互动通过通知中心异步触达相关用户，通知失败不影响互动记录本身。

![社区与用户关系域组件图](./详细设计说明/20_社区与用户关系域组件图.png)

游记发布顺序图将业务分为图片上传、内容提交、敏感词检测、帖子审核和发布后互动五个阶段。上传失败时允许用户重试；命中敏感词时拒绝提交；通过检测的帖子先进入待审核状态，只有审核通过后才进入公开内容流并允许其他用户进行点赞和评论。

![游记发布审核对象级顺序图](./详细设计说明/21_游记发布审核对象级顺序图.png)

#### 3.9.5 身份认证域（UC01、UC16、UC17）

身份认证域采用 Spring Security、JWT 与 BCrypt 组合。`UserController` 和 `UserService` 负责注册、登录和账户操作，`UserMapper` 读写用户表；`JwtFilter` 在受保护请求到达业务 Controller 前解析 Bearer Token，并通过 `SecurityContextHolder` 和 `UserContext` 向后续业务提供当前用户身份。

![身份认证域组件图](./详细设计说明/22_身份认证域组件图.png)

JWT 顺序图覆盖注册、登录和后续鉴权三个阶段。注册时密码经 BCrypt 哈希后保存；登录成功后生成 JWT 并由前端保存；后续请求经 `JwtFilter` 验证签名和有效期。Token 缺失、过期或角色不足时，请求在进入受保护 Controller 前被拒绝。

![JWT认证对象级顺序图](./详细设计说明/23_JWT认证对象级顺序图.png)

#### 3.9.6 管理后台与可观测性域（UC18、UC19）

管理后台统一承载资源维护、订单与退款、内容审核、举报工单、敏感词和日志指标等运营能力。所有 `/api/admin/**` 接口均经过管理员角色校验。`AdminController` 协调各业务 Mapper，并复用 `HotelRoomStockService`、`NotificationCenterService` 等业务 Service；`SysLogAspect` 负责记录操作人、参数摘要、执行耗时和结果状态。

![管理后台与可观测性域组件图](./详细设计说明/24_管理后台与可观测性域组件图.png)

管理员审核顺序图展示了登录鉴权、查询待审内容、审核通过或拒绝、写入审计日志和通知用户的完整过程。重复审核通过状态条件更新保持幂等；普通用户访问直接返回 403；日志落库失败仅记录告警，不回滚已经成功提交的审核结果。

![管理员内容审核代表流程对象级顺序图](./详细设计说明/25_UC19_管理员内容审核代表流程对象级顺序图.png)

### 3.12 对象级模型统一规范

1. 图片标题统一为“OBJ-UCxx + 完整用例名称 + 对象级顺序图”，图片编号 DLD-FIG-02—DLD-FIG-20。
2. 生命线从左到右按 Boundary/Page、Controller、Service、协作 Service/外部适配器、Mapper/Repository、Entity/数据库排列；不要把多个 Service 合并成一个模糊对象。
3. 同步调用使用实线实心箭头，返回使用虚线；事务范围使用 `group transaction` 或旁注；条件分支使用 `alt/else`，可选步骤使用 `opt`，批量或多轮处理使用 `loop`。
4. 每个持久化写操作旁标注引起的状态或数量变化，例如 `status: PENDING→PAID`、`availableSeats -= count`、`usedTime = now`。
5. 每张图必须至少包含一个异常或幂等分支，并在结束处标明返回对象、数据库可验证结果以及库存/状态是否回滚。
6. 图中的对象名称、接口名称、状态值和调用关系与本文类图、接口清单及数据结构保持一致。

## 4 界面设计

### 4.1 外部界面设计

#### 4.1.1 第三方与外部服务接口

- **支付接口**：不接入真实商业微信/支付宝支付，而是采用内部模拟支付逻辑或本地桩代码（Mock）实现 Webhook 回调机制，专注于验证支付完成后的订单状态机流转与库存真实扣减。
- **票务与酒店资源接口**：大交通与酒店数据**优先采用 Mock 接口响应和数据库初始化测试数据**，以此支撑前端页面的搜索与预订交互。
- **AI 接口**：统一封装 DeepSeek API 调用接口，采用 OpenAI 兼容协议；认证方式为 Bearer Auth。对于行程生成等结构化场景，要求返回严格 JSON；接口不可用、超时或返回格式异常时自动切换本地模板，确保 AI 结果可控、可解释。
- **火车公共余票同步**：通过 Playwright Java 读取公共余票页面，在支持的车站与日期场景下补充火车查询数据；同步失败不影响本地数据库查询。
- **文件接口**：支持社区图文图片的上传与获取，在前端或网关层进行图片压缩处理，降低服务器存储与带宽压力。

#### 4.1.2 统一响应格式

前后端统一使用 `Result<T>` 封装所有响应：

```json
{
  "code": 200,
  "msg": "success",
  "data": {}
}
```

前端 Axios 拦截器：`code === 200` 时直接返回 `data` 字段；非 200 抛出 Error；401 / 403 自动清除 Token 并跳转 `/login`。

#### 4.1.4 接口限流设计

`@RateLimiter` 注解用于高频写接口，`RateLimiterInterceptor` 基于 Redis 计数器 + IP 拦截超限请求：

```java
// 创建订单接口：每个 IP 每秒最多 5 次
@RateLimiter(maxRequests = 5, timeWindowSeconds = 1)
@PostMapping("/api/order/flight/create")
public Result<TrafficOrderVO> createOrder(@RequestBody TrafficOrderCreateDTO dto) { ... }
```

超限时返回 `HTTP 429`，响应体 `code=429, msg="请求过于频繁，请稍后再试"`。

### 4.2 内部界面设计

#### 4.2.1 服务间通信规范

- **服务间通信**：采用 RESTful API，统一使用 JSON 数据格式交互。主外键命名统一采用小写下划线，时间字段统一约定为 `create_time`、`update_time`，确保各子系统联调时不出现数据割裂。
- **接口文档管理**：接口契约由 Controller 定义、前端调用清单和本文接口表共同约束，并通过 Apifox/OpenAPI 维护请求、响应和错误码说明。
- **鉴权机制**：通过 JWT 在 HTTP Header 中传递 Token，后端过滤器统一进行合法性与有效期校验。
- **异步处理机制（降级设计）**：为降低验收环境搭建成本，不引入重量级消息队列（如 Kafka/RabbitMQ）。站内信通知由 `NotificationCenterService` 直接落库；操作日志由 AOP 切面记录；超时未支付订单、库存回滚和帖子 AI 审核由 Spring 定时任务（`@Scheduled`）处理。

**防超卖核心 SQL**

```sql
UPDATE tm_hotel_room
SET available_rooms = available_rooms - #{count}
WHERE id = #{roomId}
  AND status = 1
  AND available_rooms >= #{count}
```

Redis 原子预减（Lua 脚本）：

```lua
local current = redis.call('GET', KEYS[1])
if not current then
    return -2
end
current = tonumber(current)
local count = tonumber(ARGV[1])
if current < count then
    return -1
end
redis.call('DECRBY', KEYS[1], count)
return current - count
```

**数据归属规则：**

1. 每张业务表只能有一个写入责任服务；其他服务通过接口读取或请求变更，不直接跨域写表。
2. 订单服务只保存下单时必要的资源快照，资源名称和价格变化不反向修改历史订单。
3. 用户身份通过 JWT 中的稳定用户标识传递；服务不得复制用户密码、手机号等敏感字段。
4. 通知属于 AI 与消息服务，业务服务提交通知命令；通知失败不回滚已成功的订单或审核事务。
5. 运营服务通过各业务服务的管理接口执行操作；`sys_log` 可独立记录审计事件。

#### 4.2.4 跨服务接口与失败处理

下表描述逻辑服务之间的交互语义；在模块化单体中由 Controller、Service 和 Mapper 的进程内调用实现。所有写请求携带 `X-Request-Id`，幂等请求额外携带 `Idempotency-Key`。

| 调用方 → 被调用方 | 接口/事件 | 一致性要求 | 超时、重试与补偿 |
| :--- | :--- | :--- | :--- |
| SVC-AI → SVC-TRAFFIC/SVC-LOCAL | 查询交通、酒店、景点候选资源 | 只读，允许短时陈旧 | 2 秒超时，最多重试 1 次；失败时生成不含实时库存承诺的降级行程 |
| SVC-TRAFFIC/SVC-LOCAL → SVC-IDENTITY | 校验用户与旅客归属 | 强认证、只读 | 失败即拒绝下单，不进行库存扣减 |
| SVC-TRAFFIC/SVC-LOCAL → SVC-AI | `NotificationRequested` 通知命令 | 最终一致 | 业务先提交，通知失败记日志并重试，不回滚订单 |
| SVC-COMMUNITY → SVC-OPS | `PostSubmitted` 审核事件 | 最终一致 | 事件重复按帖子 ID 幂等；失败保持待审核并由调度器重试 |
| SVC-OPS → SVC-COMMUNITY | 审核通过/拒绝命令 | 状态条件更新 | 仅允许 `待审核` 状态处理；重复命令返回当前终态 |
| SVC-OPS → SVC-TRAFFIC/SVC-LOCAL | 退款审核命令 | 强一致到单订单 | 按订单号和预期状态幂等；超时后先查状态再决定是否重试 |
| SVC-OPS → SVC-TRAFFIC | 航班/车次 CRUD、订单查询 | 管理员鉴权、单资源事务 | 失败返回明确冲突；删除被订单引用的资源时拒绝或软删除 |
| SVC-OPS → SVC-LOCAL | 酒店/房型/景点/优惠券 CRUD | 管理员鉴权、单资源事务 | CSV 导入按行报告失败；库存变更携带版本或预期值 |
| SVC-OPS → SVC-IDENTITY | 用户启用/禁用命令 | 状态条件更新 | 重复命令幂等；调用失败不得伪报成功 |
| SVC-COMMUNITY → SVC-IDENTITY | 查询作者公开资料/关注状态 | 只读，隐私字段裁剪 | 500 ms 超时；失败时内容仍可显示匿名化作者信息 |
| SVC-LOCAL → SVC-LOCAL | 优惠券核销与酒店/门票订单 | 同服务本地事务 | 核销失败时整体回滚，订单与用户券状态保持一致 |
| 订单服务 → Redis/MySQL | 库存预减与最终扣减 | 数据库为最终事实源 | Redis 失败降级数据库；数据库失败立即回滚 Redis 预减；超时订单执行补偿 |

## 5 异常处理设计

### 5.1 出错信息管理

- **统一响应格式与状态码规范**：
  前后端统一定义全局响应格式结构：

  ```json
  {
    "code": 200,
    "msg": "错误描述/成功提示",
    "data": null
  }
  ```

- **核心异常分类枚举**：

  - `401`：认证失败/Token 过期（跳转登录页）
  - `403`：RBAC 权限不足（拒绝访问特定接口）
  - `404`：请求的 Mock 资源或路径不存在
  - `429`：接口限流拦截（超过 RateLimiter 阈值）
  - `500`：服务器内部兜底错误
  - `601`：库存不足/超卖拦截（针对小并发订单防超卖设计）
  - 自定义错误码说明：`ERR_001` AI 服务暂不可用；`ERR_002` 库存不足，订单关闭；`ERR_003` 登录过期，请重新认证。

- **异常处理机制**：
  - **后端**：通过 `@RestControllerAdvice` 结合统一异常处理类（`GlobalExceptionHandler`）集中捕获自定义业务异常和运行时异常，并转化为规范的 JSON 响应，不将数据库原生报错栈暴露给前端。特殊处理：数据库连接失败提示检查 `DB_PASSWORD`；表不存在提示执行 `docs/sql/init.sql`。
  - **前端**：通过 Axios 全局拦截器（Interceptors）统一拦截响应，根据 `code` 码触发统一的 UI Toast 错误提示或路由重定向。

### 5.2 故障预防与补救

- **AI 服务降级与容错**：当 DeepSeek API 接口超时、触发并发限流或 JSON 结构化输出失败时，系统**自动降级切换为本地预设的静态推荐模板或默认行程方案**，并辅以"人工校验提示"，确保 AI 规划核心页面在演示阶段的可用性。调用时需严格控制 `max_tokens` 以避免输出被中途截断导致 JSON 损坏。
- **库存防并发与回滚**：
  - 在订票、订房场景中，后端采用**数据库原子扣减（UPDATE...WHERE available > 0）**预防超卖故障；酒店房型额外通过 Redis Lua 进行预减，数据库侧最终校验，形成双重保障。
  - 利用 Spring `@Scheduled` 定时任务扫描待支付订单，确保订单超过 15 分钟仍未支付时，**自动触发库存回滚机制**释放预占资源。
- **一致性问题排查**：强制要求主外键关系（如订单表与模拟资源表）在插入时进行程序逻辑校验，防止孤儿数据导致联调崩溃。
  - **数据保障（降级）**：项目提供包含完整数据结构与初始测试数据（Mock 数据）的 SQL 初始化脚本 [`init.sql`](../docs/sql/init.sql)，保障开发、测试与验收环境中的可重现启动。

### 5.3 系统维护设计

- **轻量日志审计**：不使用 ELK 栈，改为采用 Spring Boot 本地日志文件记录（Logback），并结合 **Spring AOP 切面（SysLogAspect）** 实现系统关键操作的日志审计，将关键记录持久化到数据库 `sys_log` 表中。`SysLogAspect` 环绕通知自动拦截所有 `com.travelmate.controller` 下的方法，记录方法名、参数摘要、耗时、操作用户、IP 及成功/失败状态，日志落库失败不影响业务。
- **轻量监控大屏（成员 D 负责）**：在管理后台提供自研的数据可观测仪表盘。不引入第三方 APM 探针，基于 Redis 和本地应用内存统计并展示系统 QPS、热门查询词频、实时报错日志列表和订单财务图表，前端使用 ECharts 可视化。
- **接口限流控制**：通过 `@RateLimiter` 自定义注解结合 Redis 计数器，对下单等敏感接口配置 QPS 限流防刷，超限返回 HTTP 429。
- **数据库维护**：提供 `setup.ps1` 脚本支持一键初始化/重建数据库，使用 `mysql.exe` 直接 `SOURCE` 导入以保证中文数据编码正确。

### 5.4 故障演练与恢复验收

下表规定故障演练场景、预期行为和恢复判定指标。实验记录包含起止时间、注入方式、日志片段、业务结果、恢复时间、提交号和报告路径。

| 实验编号 | 故障注入 | 预期系统行为 | 恢复与判定指标 |
| :--- | :--- | :--- | :--- |
| CHAOS-01 | 停止 Redis 或阻断连接 | 酒店下单降级数据库原子扣减；限流/缓存异常有告警，不产生负库存 | 恢复 Redis 后执行库存同步；成功订单数等于库存扣减量 |
| CHAOS-02 | DeepSeek 超时、返回 500 或非法 JSON | UC11 返回本地模板并标记降级；UC12 返回可解释错误，不编造库存 | 外部接口恢复后新请求正常；核心页面持续可用 |

## 6 性能优化和安全设计

### 6.1 性能优化

- **Redis 缓存热点数据**：Redis 用于接口限流和酒店房型库存预减；用户会话采用无状态 JWT，Token 失效由有效期和服务端密钥轮换控制。
- **前端资源优化**：由于不部署真实 CDN 节点，前端性能优化通过 Vue 路由的**页面组件懒加载**、Vite 构建时的代码分包（Code Splitting）以及在网关层/Nginx 配置 HTTP Gzip 压缩来实现。
- **图片与 UGC 内容压缩**：针对旅途社区的 UGC 图文发布，前端在上传前进行图片尺寸裁切与压缩，减少服务器带宽与存储占用。
- **防并发与小规模削峰**：在订房场景，通过 Redis Lua 进行**预占库存的快速校验**，阻挡无效的高并发写请求直达数据库；机票/火车票和酒店最终均通过数据库原子 UPDATE 完成库存校验；通过 Spring 定时任务处理超时取消和库存回滚。

### 6.2 性能对比与弹性伸缩设计

性能结论必须来自同一提交、同一数据量、同一硬件和同一压测脚本。选取航班查询、酒店查询和酒店下单三个接口，每个场景预热后连续运行 3 次，报告中同时给出每次结果和中位数，不只报告最好值。

| 测试编号 | 接口与负载 | 对比变量 | 记录指标 |
| :--- | :--- | :--- | :--- |
| PERF-TC-101 | `GET /api/flight/search`，20/50/100 并发 | 数据库查询基线 vs 查询优化后 | QPS、P50/P95/P99、错误率、CPU、数据库连接数 |
| PERF-TC-102 | `GET /api/hotel/search`，20/50/100 并发 | 无缓存 vs 热点缓存 | QPS、P95、缓存命中率、MySQL QPS |
| PERF-TC-103 | `POST /api/hotel/order/create`，固定库存 50 | 仅数据库原子扣减 vs Redis 预减 + 数据库扣减 | 成功数、失败数、负库存数、重复订单数、P95 |

Kubernetes 正式部署包含 `identity-service`、`traffic-service`、`local-service`、`ai-service`、`community-service`、`ops-service` 六个业务服务，每个服务均配置 `Deployment`、`Service`、`readinessProbe`、`livenessProbe` 和 `HorizontalPodAutoscaler`。HPA 参数采用 `minReplicas=2`、`maxReplicas=6`、CPU 平均利用率 60%。扩容验收记录触发阈值、扩容耗时、扩容前后 P95/错误率和回落时间。

### 6.3 安全与风险控制设计

- **数据安全**：用户密码须采用加盐哈希算法（BCrypt）进行加密存储，不明文保存敏感信息。数据库密码、API Key 等敏感配置通过 `.env` 文件注入环境变量，不写入代码仓库。
- **认证与会话安全**：采用 JWT（jjwt 0.11.5，HS256）生成无状态 Token，过期时间 24h。每次重启生成新密钥，旧 token 全部失效（课程场景可接受）。
- **权限安全控制（RBAC）**：`SecurityConfig` 按接口路径配置白名单，其余接口均需认证；管理员接口额外校验 `role == 1`。确保普通用户无法越权操作管理后台的审核与资源维护接口。
- **社区内容安全审核**：采用"**敏感词词库自动过滤拦截（SensitiveWordService）+ 后台人工审核工作流**"双重机制。管理员可动态维护敏感词库，立即生效。
- **防超卖安全**：利用数据库原子 UPDATE 条件（如 `available_rooms > 0`、`available_seats > 0`）保障订单并发创建时的数据一致性；酒店房型 Redis 侧先行预减作为第一道防线。
- **防刷与限流**：前端实施按钮防抖拦截，后端 `@RateLimiter` 注解 + Redis IP 频次限制（单 IP 每秒最多 5 次下单请求），超限返回 HTTP 429。

### 7.4 容器化与 CI/CD 设计

CI/CD 流水线覆盖用例追溯检查、单体与六服务测试打包、前端构建、Playwright 冒烟、单体真实 E2E、六服务生产入口真实 E2E、质量门禁、制品归档和 Kubernetes 部署发布。

1. 前端镜像：Vite 构建 Vue 静态资源，Nginx 提供静态文件，并按接口所有权将请求分别代理到 identity、traffic、local、ai、community、ops 六服务；未登记 API 返回 404，禁止静默回落到 `travelmate-backend`。
2. 服务镜像：JDK 21 分别运行单体兼容 JAR 和六个微服务 JAR，通过环境变量注入各自 MySQL、Redis、JWT、内部服务 Token 和 DeepSeek 配置。
3. Compose：仅作为六服务本地联调与可复现实验环境；正式交付部署使用 `deploy/k8s/` 和 `travelmate` namespace。
4. Kubernetes：前端、兼容单体及六服务分别使用 Deployment + Service；MySQL 使用 PVC；Secret 保存密码/API Key；ConfigMap 保存非敏感配置；滚动更新失败时恢复更新前 digest。
5. HPA：六个业务服务均配置 `minReplicas=2`、`maxReplicas=6` 和 CPU 60% 目标，扩容前先通过 `readinessProbe`，缩容设置稳定窗口避免抖动。
6. CI 流程：`仓库/UC01—UC19/接口/部署校验 → Maven verify → 前端构建与单测 → Mock Playwright → 单体真实 E2E → 构建生产前端 Nginx 镜像 → 六服务真实 E2E → CI quality gate → 镜像扫描与发布 → K8s rollout/健康检查 → CI/CD delivery gate`。任一必需阶段失败时总门禁失败。
7. 报告归档：上传 Surefire、Playwright HTML/trace、六服务与 Nginx 日志、JAR、前端 `dist`、镜像摘要、Kubernetes rollout/健康检查和 HPA 事件。

### 7.5 验收证据门禁

满足以下条件后才能在测试报告中写“通过”：后端与六服务命令退出码为 0；前端构建退出码为 0；单体真实 E2E 与穿过生产 Nginx 的六服务真实 E2E 全部通过；数据库初始化成功；并发测试证明库存不为负且成功订单数等于库存扣减量；AI 未配置/超时/非法 JSON 三种场景均完成降级；管理员与普通用户权限边界通过；原始报告已归档并记录提交号。
